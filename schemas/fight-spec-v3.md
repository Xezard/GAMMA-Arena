# FightSpec v3

FightSpecV3 is the deterministic, side-effect-free description of one Arena
fight generated by catalog generator version 5, catalog revision 4, and layout
version 2.

The root contract is:

| Field | Contract |
| --- | --- |
| schema_version | exactly 3 |
| generator_version | exactly 5 |
| catalog_revision | exactly 4 |
| layout_version | exactly 2 |
| session_seed | normalized Park-Miller state |
| fight_index | finite non-negative integer |
| fight_id | `ga-<seed>-<index>-g5-c4-l2` |
| actor | actor paths plus a validated budgeted loadout |
| opponents | ordered human-only participants using unique resolved physical slots |
| diagnostic | stable `FightSpecV3` text |

Each opponent contains a dense logical slot, immutable physical spawn-slot ID,
resolved position and level/game vertex IDs, tactical route, equipment role,
profile/community, and validated loadout. Roles are `leader`, `primary`, or
`secondary`; leader and primary roles cannot receive pistols, while secondary
roles cannot receive primary firearms.

Actor loadout selection uses the approved weighted weapon-class/armor-class
pair algorithm. Candidate pairs are filtered by whether a concrete completion
fits the exact player budget (`player_loadout_budget`), then weighted by the
configured weapon-class and armor-class weights. After the `actor_class_pair`
draw, deterministic sorted concrete candidates are picked with the dedicated
`actor_weapon`, `actor_ammo_boxes`, and `actor_outfit` RNG streams. The knife
uses the independent `actor_knife` stream. Every concrete actor loadout remains
within the exact player budget and includes the mandatory bandage.

Opponent generation still selects enemy count before equipment. Enemy counts,
budgets, roles, factions, and loadout selection are unchanged. The deterministic
per-slot budgets sum to at most the difficulty enemy budget. The 70%-100%
affordability band with a highest-affordable fallback applies only to opponent
equipment selection. Difficulty minimum primary shares and the one-sniper
cohort limit remain validation invariants.

The resolved layout is a required independent input. Generation and validation
never invent coordinates, reuse a physical slot, call engine APIs, or mutate the
game world. Tactical routes may be reused only after every native route has been
allocated once.

`stable_encode` includes physical position, vertex IDs, route, role, equipment,
and costs in fixed order. Any catalog, layout, role, routing, position, budget,
or ordering mismatch returns a structured validation error.
